SQLAlchemy 与 Alembic — 数据库的翻译官和装修施工队

本项目版本:SQLAlchemy 2.0.51(异步)· Alembic 1.18.5 · 驱动 psycopg 3

它们是什么

SQLAlchemy 是 Python 最主流的 ORM(对象关系映射)库:让你用 Python 类和对象来读写数据库,而不用手写 SQL 语句。你定义一个 Company 类,它对应数据库里的 companies 表;操作对象,SQLAlchemy 帮你翻译成 SQL。

Alembic 是 SQLAlchemy 的官方搭档,负责 数据库迁移(migration):数据库的表结构会随需求演进(加表、加列、加约束),Alembic 把每次变更写成一个带编号的脚本,让任何环境的数据库都能按顺序「升级」到最新结构。

比喻:数据库只说 SQL 这门「外语」。SQLAlchemy 是随身翻译官 —— 你说「把这家公司存起来」,它翻译成 INSERT INTO companies ...。Alembic 是装修施工队的工程日志 —— 房子(数据库)每次改造(加房间、开窗)都留一张有编号的施工单,新房子按单子从头施工一遍,就能和老房子布局完全一致;施工单也能倒着执行,把改坏的恢复回去。

它们解决什么问题

  • 手写 SQL 易错难维护:字符串拼 SQL 拼错要运行才知道,还容易引入注入漏洞。ORM 把表结构变成类型化的 Python 代码,写错字段名 mypy 就报错。
  • 表结构失控:没有迁移工具时,「谁在哪个环境手动改过表」全靠记忆。Alembic 把结构变更纳入代码版本管理,和业务代码一起提交、评审、部署。

核心概念

模型(Model)

继承 DeclarativeBase 的 Python 类,用 Mapped[str] / mapped_column() 声明列 —— 类是表的蓝图。

会话(Session)

一次数据库对话的上下文:查询、修改先记在会话里,commit 一起生效,出错则整体回滚 —— 这就是事务。

查询表达式

select(Company).where(Company.slug == "x") —— 用 Python 语法组装查询,SQLAlchemy 生成 SQL。

迁移版本链

每个迁移脚本记着「我的上一版是谁」,连成一条链;alembic upgrade head = 从当前版本一路升到最新。

# models.py 里的写法(节选意译)
class Company(Base):
    __tablename__ = "companies"
    id: Mapped[uuid.UUID] = mapped_column(primary_key=True)
    name: Mapped[str]
    slug: Mapped[str] = mapped_column(unique=True)

# repository.py 里这样查
result = await session.execute(
    select(Company).order_by(Company.name)
)

在本项目中

位置角色
apps/api/src/company_api/models.py全部表模型:Company、Document、用户与评论相关表,以及唯一约束、检查约束 —— 数据规则写进蓝图。
repository.py 等仓储层用异步会话(create_async_engine + async_sessionmaker)执行查询;连接串 postgresql+psycopg:// 表示经 psycopg 3 驱动连 PostgreSQL。
apps/api/migrations/versions/4 个迁移脚本记录了数据库的成长史:建公司与资料表 → 加管理员会话表 → 加资料排序 → 加用户评论。
启动顺序API 容器的入口脚本先跑 alembic upgrade head 再启动服务 —— 保证代码面对的永远是最新表结构。开发时对应 make db-upgrade。

与其他技术的关系

PostgreSQL — 被翻译的那门「外语」的主人 FastAPI — repository 层被 service 层调用 Python — 一切用 uv run alembic 执行 Docker — 容器启动时自动迁移
