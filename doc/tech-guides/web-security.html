Web 认证与安全 — 只让该进来的人进来

关键词:Argon2 密码哈希 · HttpOnly 会话 Cookie · CSRF 双重校验 · sandbox iframe

要解决的三个问题

凡是有登录功能的网站,都绕不开三件事:密码怎么存才不怕数据库泄露?登录状态怎么记住才不用每次都输密码?怎么防止别人冒用你的登录状态干坏事?本项目的管理端(以及站点用户功能)给出了一套标准答案。

核心概念

密码哈希(Argon2)

数据库里永远不存密码原文,只存一段不可逆的「指纹」。登录时把输入算一遍指纹比对。Argon2 是密码哈希竞赛的冠军算法,故意算得又慢又吃内存,让暴力破解成本极高。

会话(Session)与 Cookie

登录成功后服务器发一张「手环」(随机会话令牌),存在浏览器 Cookie 里,之后每个请求自动带上,服务器凭手环认人。本项目的会话记录存在 PostgreSQL,服务器随时可以注销某个会话。

HttpOnly / Secure 标记

Cookie 上的两个保险栓:HttpOnly = 页面里的 JS 读不到它(就算被注入恶意脚本也偷不走);Secure = 只肯经 HTTPS 发送(生产必须开,即 SESSION_COOKIE_SECURE=true)。

CSRF(跨站请求伪造)

坏网站偷偷让你的浏览器向本站发请求 —— 浏览器会「自作多情」地带上 Cookie,请求就像你亲自发的。防御:写操作必须额外带一个 X-CSRF-Token 请求头,坏网站发得出请求、却拿不到令牌。

比喻:把网站想成一家会员制会所。Argon2:前台不留会员密码底单,只留一种「碎纸机碎出的独特纸屑图案」—— 能比对,拼不回去。会话 Cookie:入场后发防伪手环,凭手环通行,不用反复报密码。HttpOnly:手环焊死在手腕上,场内的小偷(恶意脚本)摘不下来。CSRF Token:办正事(写操作)除了手环还要当面对暗号 —— 隔壁店铺(恶意网站)能怂恿你走进来,却不知道暗号。

在本项目中

机制落点
密码哈希pwdlib[argon2] 库;管理员密码哈希用 make admin-password-hash(调 scripts/hash-admin-password.sh)生成后配进环境变量。
认证代码auth_routes.py(登录/登出接口)→ auth.py(校验逻辑)→ auth_repository.py(会话存取,存 PostgreSQL)。
写操作双重校验所有写接口同时要求会话 Cookie + X-CSRF-Token 头,缺一不可。
资料正文隔离公开站点用空 sandbox 属性的 iframe 展示上传的 HTML:sandbox 一开,里面的脚本不能执行、不能弹窗、不能触碰主站 Cookie —— 即使资料文件里藏了恶意代码也翻不出这个笼子。
网络纵深安全不止应用层:数据库只有 api 碰得到、容器只绑回环地址、公网只开 HTTPS 一扇门、写接口按 IP 限流 —— 层层设防。
其他细节会话令牌用 secrets 生成、邮件令牌用 hmac 签名;设计文档见 doc/AUTHENTICATION.md。
