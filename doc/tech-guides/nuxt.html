Nuxt 4 — 让 Vue 网站「先做好菜再上桌」

本项目版本:4.4.8 · 驱动公开站点 apps/web(服务端渲染 SSR)

它是什么

Nuxt 是基于 Vue 的「全栈框架」:Vue 只管画界面,Nuxt 在它外面补齐了做一个完整网站需要的其他一切 —— 路由(网址与页面的对应)、服务端渲染、数据获取、SEO 头信息、部署产物。它最重要的能力是 SSR(服务端渲染):页面先在服务器上渲染成完整 HTML,再发给浏览器。

比喻:普通 Vue 单页应用(SPA)像「生鲜到家」—— 送到你手上的是食材(空 HTML + 一大包 JS),浏览器要自己下厨(执行 JS)才能看到页面。Nuxt 的 SSR 像「热菜外卖」—— 服务器把菜做好了才送(完整 HTML),打开就能吃(看到内容),搜索引擎这位「美食评论家」也能直接品尝到内容,而不是对着一袋生食材干瞪眼。

它解决什么问题

  • SEO(搜索引擎收录):公开的资料站点需要被搜索引擎抓取,SPA 的空壳 HTML 对爬虫不友好;SSR 输出完整内容,天生利于收录。本项目的公开站点要靠搜索带流量,这是选 Nuxt 的核心原因。
  • 首屏速度:用户第一眼看到的是现成 HTML,不用等 JS 下载执行完。
  • 工程繁琐:路由配置、代码分割这些体力活,Nuxt 用「约定优于配置」全包了 —— 文件放对目录就自动生效。

核心概念

约定式目录

app/pages/ 里的文件自动变成路由,app/components/ 里的组件自动可用,app/composables/ 自动导入 —— 不写配置。

SSR + 水合(Hydration)

服务器渲染出 HTML → 浏览器显示 → Vue 在浏览器里「接管」这份 HTML,让它变成可交互的应用。这个接管过程叫水合。

Nitro 服务引擎

Nuxt 的服务器端底座:nuxt build 产出一个独立 Node 服务(node-server 输出),还能在 server/routes/ 里写小型后端接口。

routeRules 路由规则

按路径配置行为:缓存、重定向、代理转发等,一行搞定。

在本项目中

位置角色
apps/web/公开站点整体:公司列表、公司详情、资料阅读页。资料正文用一个空 sandbox 的 iframe 展示(详见安全篇)。
apps/web/app/components/DocumentReader.vue、CommentSection.vue、AuthDialog.vue、NotificationMenu.vue 等页面积木。
nuxt.config.ts 的 routeRules开发时把 /api/** 代理到本机 8000 端口的 FastAPI —— 前端开发不需要自己搭 Nginx 就能调后端。
apps/web/server/routes/healthz.get.tsNitro 小接口:容器健康检查探针,Docker 用它判断 web 服务是否活着。
生产部署nuxt build 产出 Node 服务,装进 node:24.18-alpine 容器,监听 3000 端口,由 edge Nginx 把 / 的流量转给它。

与其他技术的关系

Vue — Nuxt 的界面层就是 Vue Vite — Nuxt 的构建引擎 FastAPI — 页面数据全部来自它的接口 Nginx — 生产环境把 / 转发给 Nuxt 服务 Docker — 多阶段构建 web 镜像
