Docker 与 Compose — 标准集装箱和码头调度表

本项目:compose.yaml 编排五个服务(edge / web / admin / api / postgres)

它们是什么

Docker 把一个程序连同它需要的一切(语言运行时、依赖库、配置)打包成一个镜像,在任何装了 Docker 的机器上都能以完全相同的方式运行,运行中的实例叫容器。

Docker Compose 则是「多容器编排器」:用一个 YAML 文件描述整套系统 —— 有哪些服务、谁先启动、谁和谁连网、数据存哪 —— 然后 docker compose up 一条命令拉起全部。

比喻:集装箱发明前,货物形状各异,每换一种船就要重新装卸。Docker 就是软件界的标准集装箱:不管里面装的是 Python 服务还是数据库,外形统一,任何「码头」(装了 Docker 的机器)都能吊装。Compose 是码头调度表:五个箱子按什么顺序落位、哪些箱子之间拉专用通道、哪个箱子配保税仓(数据卷),一张表说清。

它们解决什么问题

  • 「在我电脑上能跑」的终极方案:镜像里环境完全固化,开发、测试、生产运行同一个箱子。
  • 多服务协同:本项目五个服务有启动顺序(api 要等数据库就绪)、网络隔离需求,手工管理必乱,Compose 声明式搞定。
  • 快速重建:环境坏了?容器删掉重来,一分钟恢复,数据在卷里安然无恙。

核心概念

镜像与 Dockerfile

Dockerfile 是造箱说明书(基于什么系统、装什么、怎么启动),build 出镜像,run 成容器。

多阶段构建

先在「车间箱」里编译构建,再把成品拷进一个干净的「运输箱」—— 最终镜像里只有运行所需,又小又安全。

卷(Volume)

容器是随用随扔的,数据卷是独立的持久仓库 —— 容器重建,数据还在。

网络与健康检查

Compose 里同一网络的服务能互相用服务名当域名访问;healthcheck 定期探活,依赖方可以「等它健康了再启动」。

在本项目中

compose.yaml 定义五个服务,精心设计了网络与端口边界:

服务镜像来源要点
postgrespostgres:18.4-alpine数据在 postgres_data 卷;只在 backend 网;宿主机只能从 127.0.0.1:5432 连。
api构建 apps/api(python:3.13-slim + uv)同时在 edge 与 backend 两个网 —— 它是唯一能碰数据库的服务;启动脚本先跑 Alembic 迁移;资料正文存 content_data 卷。
web构建 apps/web(node:24.18-alpine 多阶段)Nuxt SSR 服务,监听 3000,只在 edge 网。
admin构建后塞进 nginx-unprivilegedVite 打包出的纯静态文件,由小 Nginx 托管,只在 edge 网。
edgenginxinc/nginx-unprivileged:1.30.4唯一对宿主开门的入口(127.0.0.1:8080);用 depends_on: service_healthy 等三个上游全部健康才启动。

常用命令:make compose-up 整套启动、make compose-smoke 端到端冒烟测试、make compose-down 停止(保留数据卷);日常混合开发则只用 make dev-infra 起数据库容器,web/admin/api 直接在本机跑,改代码更快。

与其他技术的关系

Nginx — edge 服务就是它 PostgreSQL — 网络隔离的受益者 部署 — 镜像打包上传到 ECS 运行 工程约定 — make 命令封装 compose 操作
