# 站内账号与文章评论模块设计

## 目标

公开站点在每份研究资料的 iframe 阅读器下方提供评论区。读者使用邮箱注册站内账号，以唯一用户名发表评论和一级回复。系统审核每位用户的首次评论；管理员批准后，该用户后续发布的评论立即公开。

评论模块复用现有 Nuxt、FastAPI、PostgreSQL、Nginx 和备份体系。生产环境不增加服务。代码按账号、评论和通知三个边界拆分，避免把普通用户认证混入现有单管理员认证。

## 范围

本期包含：

- 邮箱注册、邮箱验证、登录、退出和密码重置。
- 唯一公开用户名、密码修改、邮件偏好和账户删除。
- 每份资料的公开评论列表、顶级评论和一级回复。
- 作者编辑、删除，登录用户举报。
- 首次评论审核、举报处理、评论移除和用户停用。
- 站内回复通知、审核结果通知和可退订的回复邮件。
- 桌面与移动端评论界面、管理端评论和用户视图。

本期不包含头像上传、社交登录、匿名评论、点赞、关注、多层回复、富文本、图片附件、全文搜索、自动内容审核和公开用户主页。评论只使用纯文本；系统保留换行并把经过安全处理的 URL 渲染为链接。

## 系统边界

公开站 Nuxt 应用负责注册、登录、账户设置、通知和评论交互。评论区位于 `DocumentReader` 之后，不进入资料 iframe。iframe 继续使用空 `sandbox`，上传的 HTML 与渲染后的 Markdown 不获得主站会话或评论 API 权限。

FastAPI 增加以下内部模块：

- 普通用户认证：路由、会话、邮箱验证、密码重置和账户管理。
- 评论：列表、发布、回复、编辑、删除、举报和管理员审核。
- 通知：站内通知、邮件发件箱、SMTP 适配器和后台投递循环。

普通用户使用 `user_session` Cookie；现有管理员继续使用自己的会话 Cookie。两类 Cookie、会话表、CSRF 令牌和依赖函数互不复用。管理员审核接口继续要求现有管理员会话与管理员 CSRF。

PostgreSQL 保存账号、评论、通知和邮件任务。现有数据库备份脚本自动覆盖这些表。API 进程中的后台循环领取邮件任务并投递，不新增生产 Worker。API 重启后从 PostgreSQL 继续处理未完成任务。

## 数据模型

### 用户与认证

`users` 保存：

- UUID 主键。
- 原始邮箱与规范化邮箱；规范化邮箱唯一。
- 展示用户名与规范化用户名；规范化用户名唯一。
- Argon2 密码哈希。
- `pending_verification`、`active` 或 `suspended` 状态。
- 邮箱验证时间、首次评论获批时间和回复邮件开关。
- 创建、更新时间和用户名最近修改时间。

用户名长 3 至 30 个字符，可使用 Unicode 字母、数字、下划线和连字符。服务先执行 NFKC 规范化，再用大小写折叠值检查唯一性。用户每 30 天最多修改一次用户名。评论响应从用户表读取当前用户名，因此历史评论随用户名更新。

`user_sessions` 保存会话令牌哈希、用户 ID、CSRF 令牌、创建时间和到期时间。用户会话固定有效 30 天；修改密码、删除账户或管理员停用用户时，服务删除该用户的全部会话。

`user_tokens` 保存邮箱验证、密码重置和邮件退订令牌。数据库只保存令牌哈希、用途、用户 ID、创建时间、到期时间和消费时间。邮箱验证链接有效 24 小时，密码重置链接有效 30 分钟。重发链接会使同用途的旧令牌失效。

删除账户要求重新输入密码。服务删除用户、会话、令牌、通知、举报和未投递邮件，把历史评论的 `author_id` 设为空；公开界面显示“已注销用户”，并保留讨论结构和审核记录。

### 评论与举报

`comments` 保存：

- UUID 主键、资料 ID 和可空的作者 ID。
- 可空的顶级父评论 ID。
- 纯文本正文，长度 1 至 2,000 字。
- `pending`、`published`、`rejected` 或 `deleted` 状态。
- 创建、编辑、审核和删除时间。
- 审核原因与执行审核的管理员用户名。

服务只允许父评论指向同一资料中的顶级评论。用户回复一条回复时，API 把新回复挂到该回复所属的顶级评论；数据库和服务测试共同锁定一级结构。顶级评论按 `(created_at, id)` 倒序分页，每页 20 条；每个顶级评论的已公开回复按时间正序返回。公开计数只包含 `published` 评论。

删除采用软删除。删除后的正文不再返回；有回复的顶级评论保留“此评论已删除”占位。客户端不能回复已删除、待审或被拒绝的评论。

`comment_reports` 保存评论、举报用户、原因分类、补充说明、状态和处理时间。同一用户只能举报同一评论一次，作者不能举报自己的评论。举报不会自动隐藏评论。管理员可保留评论并关闭举报，或移除评论并处理所有未结举报。

### 通知与邮件

`notifications` 保存接收用户、通知类型、触发用户、评论、资料、创建时间和已读时间。通知类型包括回复、评论获批和评论被拒。评论作者回复自己时不生成回复通知。

`email_outbox` 保存模板类型、接收地址、模板数据、尝试次数、下次投递时间、投递时间和最后错误摘要。评论或审核事务同时写入站内通知和邮件任务。SMTP 失败不回滚评论；后台循环按退避时间重试，并使用行锁防止重复领取。

回复邮件默认开启。每封回复邮件包含退订链接；用户也可在账户设置中关闭邮件。退订只关闭回复邮件，不影响邮箱验证、密码重置和站内通知。

## 账号流程

### 注册与验证

1. 读者提交邮箱、唯一用户名和密码。
2. API 规范化并校验字段，创建或更新尚未验证的账号，生成单次验证令牌并写入邮件发件箱。
3. 界面统一显示“请检查邮箱”，避免根据响应判断某个邮箱是否已经注册。
4. 用户打开验证链接，Nuxt 从 URL 读取令牌并调用验证接口。
5. API 消费令牌、启用账号并创建用户会话。

已启用邮箱再次注册时，API 不覆盖密码或用户名，只发送通用响应。用户名冲突可以明确提示，因为用户名本来公开。注册、验证邮件重发和令牌消费都接受独立限流。

### 登录与密码重置

用户以邮箱和密码登录。API 返回通用的认证失败消息，不区分邮箱不存在、密码错误或账号尚未验证。暂停账号不能创建会话。

忘记密码接口对所有邮箱返回相同响应。有效账号收到单次重置链接；重置成功后服务撤销全部旧会话并创建新会话。所有用户写接口同时校验 `user_session` Cookie 和 `X-CSRF-Token`。

## 评论与审核流程

未获得 `first_comment_approved_at` 的用户发布评论或回复时，API 写入 `pending`。作者在公开评论区看到带“待审核”标记的私有版本，其他读者看不到。用户在首条评论获批前连续提交的其他评论继续逐条待审。

管理员批准一条待审评论时，在同一数据库事务中完成以下操作：

- 把该评论改为 `published`。
- 若作者仍为启用状态且尚未受信任，写入首次获批时间。
- 为作者创建审核结果站内通知。
- 如果该评论是回复，为被回复用户创建回复通知和邮件任务。

批准不会自动发布该用户已有的其他待审评论。用户受信任后，新评论和回复直接写为 `published`，回复通知与评论在同一事务中创建。

管理员拒绝待审评论时记录原因并通知作者。管理员移除已发布评论时将其软删除。停用用户会撤销该用户全部会话并阻止新会话；已有评论继续公开，管理员按评论逐条处理。

作者可编辑自己的待审或已发布评论。待审评论编辑后仍待审；已发布评论编辑后继续公开并显示“已编辑”。本期不保存公开的修改历史。作者可删除自己的待审或已发布评论。

## API 契约

普通用户认证使用 `/api/v1/user-auth` 前缀，避免与现有管理员 `/api/v1/auth` 混淆：

- `GET /api/v1/user-auth/session`
- `POST /api/v1/user-auth/register`
- `POST /api/v1/user-auth/verify-email`
- `POST /api/v1/user-auth/login`
- `POST /api/v1/user-auth/logout`
- `POST /api/v1/user-auth/password-reset/request`
- `POST /api/v1/user-auth/password-reset/confirm`

账户与通知接口：

- `GET /api/v1/users/me`
- `PATCH /api/v1/users/me/profile`
- `PATCH /api/v1/users/me/password`
- `PATCH /api/v1/users/me/preferences`
- `DELETE /api/v1/users/me`
- `GET /api/v1/users/me/notifications`
- `PATCH /api/v1/users/me/notifications/{notification_id}`
- `POST /api/v1/users/me/notifications/read-all`

评论接口：

- `GET /api/v1/documents/{document_id}/comments`
- `POST /api/v1/documents/{document_id}/comments`
- `GET /api/v1/comments/{comment_id}/thread`
- `PATCH /api/v1/comments/{comment_id}`
- `DELETE /api/v1/comments/{comment_id}`
- `POST /api/v1/comments/{comment_id}/reports`

管理员接口使用 `/api/v1/admin` 前缀：

- `GET /api/v1/admin/comments`
- `POST /api/v1/admin/comments/{comment_id}/approve`
- `POST /api/v1/admin/comments/{comment_id}/reject`
- `POST /api/v1/admin/comments/{comment_id}/remove`
- `GET /api/v1/admin/comment-reports`
- `POST /api/v1/admin/comment-reports/{report_id}/resolve`
- `GET /api/v1/admin/users`
- `POST /api/v1/admin/users/{user_id}/suspend`
- `POST /api/v1/admin/users/{user_id}/restore`

OpenAPI 继续作为前后端契约来源。列表响应包含稳定游标；API 不返回邮箱、密码哈希、服务器路径、令牌哈希、IP 或内部投递错误。

## 公开站界面

`app.vue` 在 `DocumentReader` 后渲染评论区。阅读器 iframe 保持独立滚动，评论区使用外层页面滚动。两者之间使用清晰标题和间距标出边界，不把评论区包装成嵌套卡片。

评论区按以下状态显示：

- 未选择资料时不显示。
- 列表加载失败时显示局部错误与重试，文章保持可读。
- 未登录时显示公开评论，并在编辑器位置提供登录入口。
- 已登录时显示编辑器、自己的待审评论和作者操作。
- 会话过期时保留草稿，登录成功后恢复编辑器。

登录、注册、验证提示和忘记密码使用对话框，不离开当前文章。顶栏增加通知图标和用户菜单。账户界面提供用户名、密码、回复邮件开关和账户删除。

通知和邮件使用 `/?company=<uuid>&document=<uuid>&comment=<uuid>` 深链接。公开站按参数选择公司和资料，再通过 thread 接口取得目标评论所属的顶级讨论，不依赖目标是否位于评论列表首屏。评论加载完成后页面滚动到目标并短暂强调。目标评论已删除或不可见时，界面打开对应资料并显示简短说明。

移动端沿用现有目录抽屉。iframe 阅读器之后显示同一评论区；编辑器、评论操作和一级回复在 320px 宽度下不能造成横向滚动。

## 管理端界面

管理端主导航增加“评论”和“用户”。评论视图提供待审核、举报和全部评论三个标签；每行显示用户名、内容摘要、资料标题、时间和当前状态。

待审操作包括批准、拒绝和暂停用户。拒绝要求管理员填写简短原因。举报处理包括保留评论或移除评论。并发审核造成状态已经变化时，API 返回 409，界面刷新该行并说明内容已由其他操作处理。

用户视图支持按用户名或邮箱搜索，显示验证状态、首次获批时间、评论数和账号状态。管理员可以暂停或恢复用户，但不能查看密码、会话令牌或验证令牌。

## 安全与滥用控制

- 密码使用 Argon2；普通用户会话令牌和一次性令牌只以 SHA-256 哈希入库。
- 生产 Cookie 使用 `HttpOnly; Secure; SameSite=Strict; Path=/`。
- 注册、登录、重发邮件、密码重置、评论、编辑和举报按 IP 与账号限流。
- 所有用户和管理员写请求验证对应会话与 CSRF，不能交叉使用。
- API 只接收纯文本评论，统一转义用户名和正文；安全链接转换不允许脚本协议或自定义 HTML。
- 资料 iframe 保持空 `sandbox`，评论功能不修改上传文件或 Markdown 展示模板。
- API 日志不记录密码、Cookie、CSRF、邮箱验证令牌、密码重置令牌或完整邮件正文。
- 邮件模板不插入未转义的评论 HTML。

系统首期使用邮箱验证、首次评论审核和限流控制滥用。验证码与自动内容审核不在本期范围；出现持续机器注册或垃圾评论后再接入 Turnstile 或内容审核服务。

## 错误与并发

评论请求使用独立加载和错误状态。评论列表失败、通知失败或 SMTP 失败不影响文章目录和 iframe。发布失败时前端保留草稿；401 触发登录，403 显示 CSRF 或账号状态错误，409 用于重复用户名、重复举报和过期审核状态，422 用于字段校验。

评论发布、站内通知和邮件任务使用单个数据库事务。邮件循环通过 `FOR UPDATE SKIP LOCKED` 领取任务，并用投递时间保证成功任务不重复发送。进程在发送成功后崩溃仍可能造成 SMTP 重复投递；邮件模板和通知文案不承诺严格一次投递。

资料删除通过外键级联删除评论、举报和相关通知。账户删除与评论匿名化在一个事务中完成。分页游标包含创建时间和 UUID，避免同一时间写入导致丢项。

## 邮件配置

新增以下配置类别：

- 用户注册功能开关。
- 评论写入功能开关。
- SMTP 主机、端口、用户名、密码、TLS 模式、发件地址和站点公开地址。
- 邮件重试次数、初始退避时间和后台领取间隔。
- 开发或测试邮件后端。

生产环境没有 SMTP 配置时必须保持 `USER_REGISTRATION_ENABLED=false`。公开站显示“注册暂未开放”，已有用户仍可登录；验证邮件和密码重置依赖 SMTP，因此正式开放前必须配置一个支持标准 SMTP 的邮件服务和发件域名。`COMMENT_WRITES_ENABLED=false` 时保留评论读取，API 拒绝发布、编辑、删除和举报，供部署回退和维护使用。

本地开发使用控制台邮件后端。Compose 冒烟测试使用仅在测试环境允许的文件捕获后端，从临时文件读取验证链接。API 在生产环境拒绝启动测试邮件后端，防止令牌写入生产日志或文件。

## 测试

API 模型与迁移测试覆盖外键、唯一约束、状态枚举、级联删除和匿名化。仓储与服务测试覆盖：

- 注册、重复注册、邮箱验证、令牌过期和重发失效。
- 登录、密码重置、会话撤销、CSRF 和停用账号。
- 首次评论待审、批准后受信任、连续待审不批量放行。
- 一级回复约束、跨资料回复拒绝、稳定分页和公开计数。
- 作者编辑删除、权限拒绝、重复举报和管理员状态冲突。
- 站内通知、邮件偏好、退订、发件箱领取和失败重试。
- 评论纯文本转义、危险链接拒绝和响应隐私字段隔离。

Web Vitest 覆盖评论加载与重试、登录后草稿恢复、私有待审状态、一级回复、编辑删除、通知定位和 320px 布局。Admin Vitest 覆盖待审筛选、批准拒绝、举报处理、用户停用和 409 刷新。

Compose 冒烟测试使用测试邮件后端执行“注册、验证、首次评论、管理员批准、回复、站内通知”主路径。`make check` 继续覆盖根目录契约测试、两个前端的 lint/typecheck/test/build 和 API 的 Ruff、Mypy、Pytest。

## 上线与回退

部署先运行增量 Alembic migration，并保持用户注册关闭。迁移完成后部署 API、Web 和 Admin，再配置 SMTP、发件域名与 HTTPS 公开地址。发送测试邮件成功后打开注册开关。

上线初期管理员关注待审数量、邮件失败数、注册和评论限流命中。需要回退时先关闭注册和评论写入，保留公开评论读取；旧版应用会忽略新增表，数据库数据继续由现有备份保存。破坏性回滚迁移不作为日常回退手段。

## 验收

- 用户可通过邮箱验证建立账号，以唯一用户名登录并重置密码。
- 每份资料的 iframe 下方显示公开评论、评论编辑器和一级回复。
- 新用户的评论仅本人和管理员可见；管理员批准后公开，后续新评论即时公开。
- 作者可编辑和删除，其他登录用户可举报，管理员可审核、移除和停用用户。
- 回复与审核结果生成站内通知；回复邮件可关闭和退订，SMTP 失败可重试。
