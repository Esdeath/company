# 资料手动排序设计

## 目标

管理员可以在单个公司的资料目录中拖动整行调整先后顺序。管理端和公开站点都按这套顺序展示资料。管理员没有调整新上传的资料时，系统把它们追加到该公司资料目录末尾。

本次改动只调整同一公司内的资料顺序，不支持跨公司拖动，也不改变公司顺序、资料标题、正文存储或 iframe 阅读边界。

## 顺序模型

`documents` 表新增非空整数列 `sort_order`。API 按 `sort_order ASC, id ASC` 返回单个公司的资料，`id` 只处理异常重复序号，正常写入不会产生重复序号。

Alembic 迁移按每个公司当前的展示规则 `uploaded_at DESC, id DESC` 生成从零开始的连续序号。因此迁移不会改变已有资料的视觉顺序。迁移同时为 `(company_id, sort_order)` 建立普通索引，并给 `sort_order` 添加非负约束。

上传资料时，仓储层锁定所属公司记录，在同一事务中读取该公司的最大 `sort_order`，再写入 `max + 1`。空目录从零开始。同批文件沿用现有串行处理，每个成功文件按上传请求中的文件顺序追加；失败文件不占序号。公司行锁防止并发上传取得相同的末尾序号。

删除资料后允许序号存在空隙。下一次手动排序会重新写成连续序号。空隙不影响排序，也避免删除时更新其余资料。

## API 契约

新增请求模型：

```json
{
  "document_ids": ["资料 UUID", "资料 UUID"]
}
```

管理端调用 `PUT /api/v1/companies/{company_id}/documents/order`，提交该公司的完整资料 ID 顺序。该接口沿用管理员会话 Cookie 和 `X-CSRF-Token` 要求。

服务端在公司行锁内读取该公司的资料，并执行以下校验：

- 公司必须存在。
- `document_ids` 不能包含重复值。
- 请求必须包含该公司的全部资料，不能遗漏或加入其他公司的资料。

校验失败时不修改任何序号。公司不存在返回 `404`；资料集合不匹配或有重复值返回 `422`。保存成功后接口返回按新顺序排列的完整 `DocumentRead` 数组，管理端直接用响应替换本地目录。

`DocumentRead` 增加 `sort_order`，管理端和 Web 类型同步增加该字段。公开列表接口继续使用原路径，不增加客户端排序。

## 管理端交互

`DocumentList` 让每个资料行成为可排序项。用户可以从标题、格式标记或行内空白区域开始拖动；输入框、保存名称和删除按钮不触发拖动，继续执行原操作。

拖动过程提供三种视觉反馈：被拖行降低不透明度，目标位置显示清晰的插入线，列表保持原有行高与两列布局。鼠标指针在可拖区域显示抓取状态。组件不添加卡片、弹窗或独立保存按钮。

组件使用 Pointer Events 统一处理鼠标、触控笔和触屏，不依赖桌面浏览器的 HTML Drag and Drop API。拖动达到小距离阈值后才开始重排，避免点击标题时误触。组件根据指针所在行的中点计算插入位置，并在指针释放时发出完整的新 ID 顺序。

资料行可以获得键盘焦点。聚焦后使用 `Alt+ArrowUp` 和 `Alt+ArrowDown` 移动一位，随后走同一保存流程。页面用视觉隐藏的说明和 `aria-live` 状态区播报“已移到第 N 项”、保存成功或恢复原顺序，触屏和键盘操作获得同样结果。

放下后，`App.vue` 先保留旧数组快照，再显示新顺序并调用排序 API。保存期间禁止再次拖动以及该目录内的重命名和删除，避免并发操作覆盖顺序。成功后使用服务端响应；失败后恢复快照，并通过现有页面错误区域显示原因。切换公司或会话失效时，现有请求代次和登录恢复逻辑继续阻止旧响应写入当前目录。

## 公开站点

Web 的 `listDocuments` 和 `LibraryDirectory` 继续按 API 数组顺序渲染。首次打开公司时选择数组第一项，刷新时继续保留仍然存在的当前资料。Web 不根据上传时间、标题或 `sort_order` 再排序，避免管理端与公开站产生两套规则。

## 组件边界

- Alembic 迁移负责字段、回填、约束和索引。
- `SqlAlchemyLibraryRepository` 负责末尾序号分配、公司级锁和事务重排。
- `LibraryService` 负责把仓储记录映射为公共模型，并把资料集合不匹配转换为明确的领域错误。
- FastAPI 路由负责 HTTP 状态码、认证和 CSRF 边界。
- `DocumentList.vue` 负责指针与键盘排序交互，只发出完整顺序。
- `App.vue` 负责 API 调用、忙碌状态、乐观显示和失败恢复。
- Web 只消费 API 顺序。

## 测试

API 测试覆盖迁移元数据、已有资料顺序回填规则、上传追加、并发保护所需的公司锁、列表按 `sort_order` 返回、有效重排、重复 ID、遗漏 ID、跨公司 ID、未知公司、会话与 CSRF。

管理端测试覆盖完整顺序请求、整行指针拖动、交互控件不触发拖动、键盘移动、保存期间禁用操作、成功采用响应、失败恢复旧顺序以及公司切换后的过期响应保护。

Web 测试用与上传时间相反的 API 数组证明目录保留服务端顺序。现有首项选择、当前资料保留和资料移除修复测试继续通过。

## 验收

- 管理员可以用鼠标或触屏拖动资料整行，输入框和按钮仍可正常使用。
- 管理员可以用键盘调整同一顺序，并听到状态播报。
- 放下后立即保存；失败时恢复放下前的顺序并显示错误。
- 管理端刷新后保留已保存顺序，公开站点展示相同顺序。
- 新上传的成功资料按选择顺序出现在目录末尾。
- 迁移后已有资料保持当前“新上传在前”的视觉顺序，直到管理员调整。
- 重复、遗漏或跨公司的排序请求不会修改数据库。
- API、Admin、Web 和根目录工程检查通过。
