# 公司顺序管理设计

## 目标

管理员可以在管理端使用上移和下移按钮调整公司目录顺序。每次操作把公司移动一位并立即保存。公开站点的桌面目录和移动端抽屉按照同一持久化顺序展示。

新建公司追加到目录末尾，不改变管理员已经排好的公司顺序。

## 数据模型与迁移

`companies` 表增加非空 `sort_order` 大整数列，并增加非负检查约束和顺序查询索引。

迁移按照当前公司目录规则初始化顺序：先按去除首尾空白后的公司名称做不区分大小写的升序排列，再以公司 ID 升序处理同名公司。序号从 `0` 开始连续生成。这样升级前后的首次显示顺序保持一致。

创建公司时锁定公司顺序写入范围，读取当前最大 `sort_order`，并把新公司写入末尾。空目录中的第一家公司序号为 `0`。

## API 契约

`CompanyRead` 增加 `sort_order`。`GET /api/v1/companies` 按 `sort_order`、公司 ID 升序返回，ID 只作为异常重复序号时的稳定后备排序。

新增管理员接口：

```http
PUT /api/v1/companies/order
Content-Type: application/json
X-CSRF-Token: <token>

{"company_ids":["...","..."]}
```

请求必须包含当前全部公司的 ID，且不能重复。服务端在同一事务中锁定公司记录，确认请求集合与数据库集合完全一致，然后按照数组位置把 `sort_order` 重写为从 `0` 开始的连续序号。成功响应为完整、已排序的 `CompanyRead` 列表。

重复 ID 由请求模型返回 `422`。缺少公司、包含未知公司或目录在请求期间发生变化时返回 `422`，错误信息为“公司顺序与当前目录不一致”。接口继续沿用管理员会话和 CSRF 保护。

## 管理端交互

公司列表沿用资料目录的上移和下移按钮，不增加拖拽或序号输入。每个按钮使用方向图标并提供包含公司名称的可访问名称和悬浮提示。第一家公司禁用上移，最后一家公司禁用下移；只有一家公司时两个按钮都禁用。

有效点击计算完整的新公司 ID 顺序并提交。`App.vue` 先乐观更新公司数组，再调用完整顺序 API：

- 保存成功时采用服务端响应，并通过礼貌状态区域播报“公司顺序已保存”。
- 保存失败时恢复操作前的数组，显示可读错误，并播报“顺序保存失败，已恢复原顺序”。

保存期间禁用公司排序、公司切换和新建公司，防止并发操作覆盖顺序或改变当前选择。当前选中的公司按 ID 保持选中，移动公司不会重新加载其资料。

新建公司成功后，管理端先把返回的公司追加到本地列表末尾并选中它；随后刷新公司列表时采用服务端顺序。刷新失败时保留已经成功创建且位于末尾的公司，并显示刷新警告。

移动端公司下拉框不显示排序按钮，但选项顺序与桌面公司列表一致。排序按钮只出现在桌面公司目录中；移动端管理员仍可查看保存后的顺序。

## 公开站点

公开站点不自行排序公司。现有应用状态、桌面目录和移动端抽屉继续按 `GET /api/v1/companies` 的数组顺序渲染，因此保存后刷新页面即可看到管理端设定的位置。

首次进入站点时仍选择返回列表中的第一家公司。已有包含 `company` 参数的深链接继续按公司 ID 选择目标，不受顺序调整影响。

## 错误与一致性

完整集合校验防止部分顺序提交误删或遗漏公司。数据库事务和行锁保证校验与序号更新使用同一份公司集合。

管理端只允许一个公司排序请求在途。无效长度、重复 ID 或未知本地 ID 不发出请求。鉴权失效继续使用现有回到登录页的处理。

## 测试

API 测试覆盖：

- 迁移按升级前的名称规则生成连续顺序。
- 公司列表按 `sort_order` 返回，新建公司追加到末尾。
- 完整顺序替换成功，并重写连续序号。
- 重复、缺失和未知公司 ID 被拒绝。
- 排序接口要求管理员会话与 CSRF 令牌。

管理端测试覆盖：

- 首项上移、末项下移和单项列表的禁用状态。
- 每次点击只移动一位并发出完整 ID 顺序。
- 保存成功采用服务端结果，失败恢复旧顺序。
- 保存期间禁用公司排序、切换和新建。
- 新建公司在成功响应后位于末尾。
- 移动公司保持当前公司和资料不变。

公开站点测试明确公司目录保留 API 返回顺序，并确认桌面与移动端使用相同数组。

## 范围外

本次不增加公司重命名、批量移动、拖拽排序、序号输入或公开站点实时推送。公开站点在下次请求公司列表时获取新顺序。
